## 2. 不变的目标与边界

### 2.1 四页职责

| 页面 | 职责 | 分类呈现 |
|---|---|---|
| `/chords` | 查询已知名称的和弦、浏览支持集合、连接基础学习与练习 | 根音和类型可以分别选择，也可以组合筛选 |
| `/chords/a-minor` | 查阅并练习 Am | 明确当前根音 A、类型 minor；主页面始终对应 Am |
| `/chords/a-major` | 查阅并练习 A major | 明确当前根音 A、类型 major；主页面始终对应 A major |
| `/chords/c-major` | 查阅并练习 C major | 明确当前根音 C、类型 major；主页面始终对应 C major |

详情共享母版，但保留每页正确的原始解释、例子、资源与差异，不能只替换名字。

### 2.2 本轮不做

不改品牌、Logo、Favicon、全站主题、全站首页 Hero、已确定的 URL、canonical 或页面搜索意图。不重做其他栏目的内容，不升级框架或更换 UI 库，不为数量目标批量发布新页面。

全站导航的外观、现有入口默认保持；只评估 Chords 相关分组和四页内链。涉及共享 Header、布局、主题或全站导航变更，必须单独标明影响，不能悄悄附带修改。

本轮不把 MIDI、麦克风识别、账号、付费、收藏、全站搜索、进阶爵士训练设为上线依赖。

### 2.3 两种“正确”不要混淆

代码与页面说明的是**现在怎么实现**；已确认需求规定的是**目标是什么**。不能因为仓库里存在一个错误就将它固化，也不能因为旧提案写了某个模块就认定仓库缺少它。

当前仓库、本地渲染与线上版本不一致时，记录版本差异。主题基线无法唯一确定时，只阻塞视觉实施，不妨碍完成内容盘点与架构审阅。

### 3.1 主题锁定：必须可核对

记录下列项目的**现有实现**：页面背景、普通表面、文字、次要文字、边框、主操作、hover/focus/selected、琴键高亮、Header/Footer，以及现有字体、圆角和阴影。

优先复用现有语义 token 或组件。项目尚未令牌化的样式不等于要先建立一套全新设计系统；先复用现有机制，必要的别名或局部抽取在批准范围内进行。

先使用仓库已有浏览器/测试工具取得当前页面截图；没有相应能力时，如实说明，不能将代码推测写成视觉通过，也不能改用旧生成图作为替代证据。

建议检查宽度为 1440、768、390、320 CSS px；这是测试范围建议，不是用户设备分布的事实。先完成四页桌面与手机基线，复用已取得的证据，不反复全站扫描。

## 4. 内容保留规则：先登记，再排版

### 4.1 逐项内容表

每条现有内容至少记录：

| 原页面/源文件 | 原内容 ID/标题 | 具体保留内容 | 动作 | 新位置 | 理由与证据 |
|---|---|---|---|---|---|
| 由仓库填写 | 原锚点或稳定 ID | 正文、图、表、FAQ 条目、链接或操作 | KEEP / MOVE / ADD / CORRECT / PROPOSE_REMOVE | 新章节/组件 | 为什么改变 |

- **KEEP**：内容与入口保留。
- **MOVE**：调整位置，但全部信息、适用条件、相关图示和资源仍可访问。
- **ADD**：确有缺口，并有内容或功能交付支撑。
- **CORRECT**：有证据的错误或已经失效的说明；保留有用部分，记录前后差异。
- **PROPOSE_REMOVE**：只能提出有证据的移除建议；实施前需进入获批清单。不能因为拥挤、很长、看起来不高级就删除正确内容。

合并章节也必须逐项映射。隐藏的打印层、无 JS 层、桌面/手机导航可能有不同用途，不能仅因文本重复就删掉。可见的重复“当前选中”标签要通过 DOM 和状态复测再判断。

**所有正确内容没有去向的数量必须为 0。**没有去向的条目不准被“新版更简洁”覆盖过去。

### 4.2 已取得的网页线索，不是完整基线

[已核实｜2026-09-11 网页正文抓取] `/chords` 仍可读到查阅集合、读图说明、大小和弦对比、打印说明、问答和详情入口。抓取正文显示 19 个名称，并区分扩展后的交互集合与原九和弦 PDF。[S1]

[已核实｜同轮抓取] Am 页可读到定位音符、原位例子、转位表、构成原理、文字练习、打印与问答。[S2]

A major、C major 本轮工具未取得正文。这不等于两页有故障，也不允许用 Am 的内容代替它们的原内容。四页均应由 Codex 在同一仓库版本补齐盘点。

不把上面的数量写成永久常量，也不将这个提案当作线上已完成验收的证明。

## 5. 根音 × 类型：同一数据系统的两个维度

### 5.1 术语和数据边界

[已核实] 三和弦的根音、性质和转位不是同一个属性；转位由最低的和弦音决定。[S7、S8]

本方案采用：

| 维度 | 示例 | 不应混入 |
|---|---|---|
| 根音拼写 `rootSpelling` | C、C♯、D♭、A、C♭ | 不命名成“12 个调” |
| 和弦类型 `qualityId` | major、minor；后续可扩展 dominant7、major7 等 | 左右手、转位、调性 |
| 具体排列 `voicing` | 具体音高、音区、最低音 | 不作为新的和弦类别 |
| 练习/演奏情境 | 单手练习、双手伴奏 | 不塞进类型筛选 |

根音音高类别与音名拼写分开保存。不要为了做“12 个按钮”丢弃现有 C♭，也不要把 C♯ 和 D♭ 的内容自动当作同一份拼写。首版默认按真实根音拼写精确筛选，显示已支持的选项。

“等音分组”可以以后作为展示方式评估，但不能更改底层音名和来源。没有必要为排列整齐一次实现所有拼写。

### 5.2 查询行为

| 用户选择 | 预期 |
|---|---|
| 根音全部＋类型全部 | 显示当前全部已发布、可用的数据对象 |
| 根音 A＋类型全部 | 显示实际支持的 A-root 对象 |
| 根音全部＋minor | 显示实际支持的 minor 对象 |
| 根音 A＋minor | 匹配 Am；有详情则提供真实链接 |
| 没有匹配对象 | 说明当前集合尚未收录，保留选择，提供清除一项/全部筛选；不能说该和弦不存在 |

两种选择无先后强制。显示“根音/类型/结果数/清除”的当前状态，不做需要点击才能看到正确初始答案的向导。

类型选项来自实际发布数据；不要将几十种未来类型展示成已经可查的按钮。知识地图可以说明未来覆盖，但不与可用筛选混在一起。

### 5.3 页面与索引

筛选不自动创建 `/chords/c` 或 `/chords/major` 等新页面；不生成“根音×类型×手别×转位”URL 笛卡尔积。详情维持原 URL，显示当前根音和类型；换到另一对象应使用已存在详情链接，不能让 `/chords/a-minor` 的主内容变成 A major。

首版没有必要新增可分享参数；已有 URL 状态则保留并核验。引入参数需单独设计无 JS、静态部署和 canonical 行为，不为了筛选强行改成按请求渲染。

正向查询建议称 `Browse chords` 或沿用现有 `Piano Chord Chart`；“按已知音符反查名称”才是另一个工具任务，不能因为更换标签就宣称反查已经实现。

## 6. 页面结构与空间设计

### 6.1 一组共同规则

**允许页面更长，不靠删内容、缩小文字或把所有正文折叠来显得不拥挤。**

建议以现有容器和排版层级为基础：一个主要阅读流；一个章节一个任务；避免卡片里面再套卡片；不做四到六列微型琴键卡片，不默认增加整页固定的大预览侧栏。

长解释优先普通正文、列表和表格；不要每个概念都做一个小色块。两个确需对比的对象可以并排，手机按顺序堆叠。

建议从现有 spacing scale 中选择：桌面章节间距约 48–64 px、手机约 32–40 px；卡片间距约 20–24 px。这些是审阅起点，不是已取得的本站 token 或必须硬编码的值。字体家族、色彩、基础文字尺度默认不变。

正文可读宽度与琴键操作区的宽度分开处理；不要用同一窄栏挤琴键，也不要把长段落拉成整屏一行。具体宽度依现有设计和实测确定。

### 6.2 `/chords` 建议顺序

```text
现有 Header（原主题、原品牌）
标题、现有准确简介
页内目录：查和弦 / 读图与理论 / 左右手 / 练习 / 打印

01 查和弦
   根音筛选 + 和弦类型筛选 + 清除 + 真实结果数
   现有结果集合：桌面优先两列，手机一列
   每项保留名称、准确音符、音区、键位、操作、可用详情入口

02 怎么读这张图
   保留现有解释与步骤，包括音名/八度/升降号/显示范围

03 大和弦与小和弦：改变三度
   保留现有表格、例子、对比图和解释
   有缺口时再加入一段“和弦、根音、类型、音级”说明

04 左右手与转位入门（新增或整合现有内容）
   简明解释；当前对象的具体指法留在详情页
   不设“左手一律低音、右手一律和弦”的规则

05 练习起点（增量）
   一个真实可用的任务，或到已发布练习的链接
   原有文字练习若存在必须保留，不以入口卡片替代

06 打印与下载
   原文件与范围说明，当前对象/当前筛选的打印操作

07 常见问题（全部正确条目）
08 已有详情与相关学习入口（按关系组织，不丢原入口）
09 来源与适用范围
现有 Footer
```

“页内目录”是章节锚点，不是让理论、练习正文互相卸载的客户端 Tabs。当前有“搜索本页”功能时先记录、保留；能否与目录合并另行评估，不自动删除。

**默认不新增统一的大侧栏预览。**先保留现有各结果的核心交付，用卡片宽度、章节留白、标签和按钮主次缓解拥挤。只有审阅证明统一工作区确实更好、且所有原功能可追溯，才在报告中提出替代方案，经确认后做。

不要为了放更多卡片裁掉琴键上的实际音区和升降号。没有详情页的数据对象可以继续查阅、播放和打印，但不能展示跳到不存在页面的“详情”按钮。

### 6.3 三个详情页的共享顺序

```text
现有 Header
面包屑 + 当前对象 H1 + 准确直接答案
当前根音与类型标识 + 查其他和弦入口
轻量章节目录

01 当前和弦工作区
   音符、公式、当前排列、低音、完整键盘
   原播放/分解播放/停止/当前打印/实际PDF入口
   音色、音区与无JS说明保留

02 原位例子与如何找这些键
   保留每页自己的说明、步骤和注意事项

03 转位
   原完整对照表、原位/第一/第二转位说明
   可切换，但所有参考行保留在HTML里

04 左右手示例（新增或整合）
   针对已核对的“排列＋音区＋手别”的示例
   不把无来源的通用数字强塞进图示

05 构成原理与比较
   保留现有全文、对应对象的例子
   需要补充的对比紧邻解释，不另造重复百科

06 原文字练习 + 新增一个带反馈练习
   新旧并存，明确各自能判断的范围

07 原打印章节与文件说明
08 原FAQ（逐条保留正确内容）
09 有理由的下一步、来源与核查范围
现有 Footer
```

实际原页面有额外模块，必须加入新顺序，而不是因上面没有列出就删除。Am 的章节名称不能直接套到 A major/C major；母版共享模块能力，页面数据保留专属内容。

### 6.4 内容差异的审阅方向

| 详情 | 可审阅/补充的重点，不是当前缺陷断言 |
|---|---|
| Am | C natural 与 C♯ 的比较；Am/C 的低音含义；音符与八度的区分 |
| A major | C♯ 的键位和拼写；同音区对比 Am；转位中的实际低音 |
| C major | C 和弦与 C 大调音阶的区别；音级与手指号区分；有语境的共同音练习 |

所有新增乐理先根据已有数据和可靠资料核对。不要以“minor＝悲伤、major＝快乐”作为和弦定义，也不要为了营销重写正确的直接答案。[S7]

### 6.5 手机设计

使用完整长页面，不把主要理论、定位步骤、转位说明和文字练习全部默认收进手风琴。FAQ 可以使用原生 `details` 等方式，内容仍预渲染；是否折叠是可读性决定，不是移除。

根音多时优先带明确标签的可访问选择控件；标签条只有实际可操作时才采用，不强制把全部拼写挤成一行。琴键区域与转位表需要局部滚动时，应有明确边界，页面本身不溢出。

不叠加新的移动底栏、固定播放栏和多层 sticky 导航。保持浏览器缩放；不要用禁止全页缩放的方式处理琴键误触。[已核实] W3C 的文本缩放要求涉及放大后仍不丢内容或功能。[S9]

## 7. 交互规格：不是画出按钮就算完成

以下为目标行为。先核查现有能力，已有正确实现复用，不默认重写。

| 操作 | 预期反馈与状态 | 必须保留的边界 |
|---|---|---|
| 改根音/类型 | 更新匹配集合和结果数；保留仍有效的选择 | 不自动播放，不把页面变成新 URL；无结果不代表音乐对象不存在 |
| 清除筛选 | 回到全部真实支持对象 | 无需刷新丢失内容；默认排序可预测 |
| 选择当前卡片（若现有此行为） | 明确当前对象，用文字/状态而非只靠颜色标识 | 与“打开详情”分开，嵌套按钮不误触导航 |
| 播放和弦 | 用户点击后播放当前对象/排列 | 首次授权、加载、失败都有反馈；不能宣称是真钢琴录音 |
| 逐音播放 | 播放当前明确顺序的相同音符 | 不使用上一对象的缓存状态 |
| Stop | 终止当前播放与待播调度，恢复可操作状态 | 多卡片共用音频协调时不出现叠播；不影响静态参考 |
| 切换转位 | 同步音符顺序、低音、符号、琴键、已支持谱表、指法案例、打印 | 旧播放先停止；只有一个“当前”状态；页面仍是同一个和弦 |
| 选择左/右手 | 显示对应已核对案例 | 手别本身不改变和弦身份；音区改变须明确；没有依据不显示假的指号 |
| 音名/音级/指法显示 | 明确标签模式 | 指法仅在匹配案例存在时开放；不是删掉正文中的解释 |
| 查其他和弦 | 进入存在的详情或真实中心入口 | 不悄悄在 Am URL 下替换成 A major 正文 |
| 页内目录 | 滚动到真实章节，可深链接 | 保留旧锚点或兼容锚点；内容不因未点 Tab 而不存在 |
| 当前对象/排列打印 | 固定一份当时状态的打印快照 | 与桌面当前对象一致；打印过程中不被其它操作悄悄改变 |
| 匹配结果打印 | 打印当前完整匹配集合 | 不是只打印屏幕上可见的几张；说明范围 |
| 下载原PDF | 打开实际文件，显示真实内容范围 | 新增网页内容不代表旧文件自动更新；不能改个按钮名称就承诺包含指法 |
| 新练习答题 | 显示缺音/多音/最低音等与题目对应的反馈，并可重试/看答案 | 不把点击琴键说成实体演奏水平；不自动重置原查阅状态 |

新增谱表、键盘输入、手指图、八度选择都需要真实数据与验证，不能仅因为旧生成图画了就自动实现。

### 7.1 练习的首个交付

建议只先做一个复用任务：在网页琴键上选择组成音，点击检查，得到针对性反馈。然后再扩展转位判断或大小对比。

组成音题可按音高类别判定；指定转位题必须检查最低音；指定音区题必须检查实际八度。英文文字输入还需要单独说明拼写规则，不把等音演奏和理论拼写题混为一谈。

原有文字练习与静态自查仍保留。无 JS 时至少能读题和参考答案，不显示貌似可用却不能操作的测验。

### 7.2 左右手案例要求

每个案例绑定具体 `voicingId`、手别、音序、指号、情境、来源与核查状态；不将统一 `[1,3,5]` 套用所有对象与转位。

[推断] 右手 C4–E4–A4 的最低音是 C；加上左手 A2 后，整体最低音变成 A。整体转位应按合并后的实际音高判断，不能沿用右手排列标签。依据是转位的最低音规则。[S8]

未核对的案例只列入内部缺项。该模块可暂缓，但不阻断现有正确内容与页面布局的交付；也不能为了展示成功而将 `pending` 改成 `reviewed`。

## 8. Schema：复用数据职责，不制造一个新平台

[已核实] JSON Schema 描述与验证数据结构，不负责页面渲染；Next.js 的服务端/客户端组件负责页面输出和交互。[S3、S5]

### 8.1 最小数据流

```text
现有内容与音乐数据
       ↓ 必要时添加适配层，不抹掉已有字段/来源/状态
经过校验的页面模型
       ↓
共享服务端模板：完整正文、表格、SVG、内链
       ↓
局部交互组件：筛选、音频、转位、练习
```

JSON Schema、schema.org JSON-LD、TypeScript 类型是不同用途。不要把“添加结构化数据脚本”说成完成 Schema 驱动，也不要为了拥有一个 `.schema.json` 文件重写全部数据。

### 8.2 应表达的数据职责

| 对象 | 核心字段/职责 |
|---|---|
| 和弦定义 | 稳定ID、根音拼写、类型ID、符号、音符正确拼写 |
| 排列 | 稳定ID、所属和弦、按低到高的具体音高/八度、默认显示范围 |
| 指法案例 | 排列引用、手别、对应指号、情境、来源和状态 |
| 页面内容 | 固定路由、metadata、全部原正文模块、新增已审阅模块、原锚点、FAQ和资源引用 |
| 练习 | 对象/排列引用、题型、判定模式、提示、答案、自查与反馈 |
| 关系/发布状态 | 目标ID、关系类型、展示位置、真实路由、可用状态 |
| 来源/资源 | 资料名称、链接、支持范围、核查依据；文件类型、包含内容与使用边界 |

这些是逻辑职责，不要求七个数据库、七套配置或一次性重建目录。

可利用现有校验系统；若已有类型和验证器能产生 JSON Schema 或等效校验，先证明覆盖情况。没有合适方案时，在审阅中提出最小新增依赖及理由，不直接安装。

### 8.3 校验分三层

**结构校验：**字段、枚举、数据类型与必填条件。

**语义测试：**引用存在、对象与页面一致、音符/八度/转位正确、指号数量匹配、所有发布链接有效、待核查内容不误显示。

**内容复核：**教学说法、指法适用性、来源支持范围、资源许可与实际文件内容。

Schema 通过不能证明指法最适合某个人，更不能证明引用资料允许转载图片。已有权利/来源台账必须保留。

### 8.4 共用模型的一致性

琴键、音名、声音、最低音、打印使用同一份规范化排列。谱表若存在或获准新增，也要由该排列产生。派生值不必在多个文件里人工重复维护；已有缓存/生成数据应验证一致性，而非机械删除。

保留正确的音名拼写和八度关系。显示用 Unicode 升降号与存储记号可以规范化，但不能将所有等音音名合并成一套升号列表。[S1、S7]

## 9. 预渲染与 SEO 验收

[已核实] Next.js 支持 Server Components 与 Client Components 组合，客户端组件可以参与首次 HTML 预渲染；`use client` 本身不等于空壳页面。[S3]

[已核实] App Router 的 `generateStaticParams` 可用于构建时生成路径；无需因此更改现有 URL 或迁移路由体系。[S4]

本方案的硬目标是**初次返回的 HTML 已有核心内容**。对于稳定 JSON 内容，优先保留当前可用的静态生成/预渲染策略；不要求每次访问重新算一遍 SSR。实际做法以仓库版本和部署能力为准，不照最新文档强行升级。

必须做到：

| 验收 | 通过标准 |
|---|---|
| 原始响应HTML | 当前页答案、正文、图示、转位参考、FAQ、内链存在于实际标签；不只是脚本里的字符串 |
| 禁用JS | 能阅读正确原内容、全部参考结果/转位表和实际资源；过滤/音频不可用有说明 |
| 三条详情直达 | 各自输出正确对象，不共用默认 C 或只替换H1 |
| 模板 | 核心内容不依赖 `useEffect` 后请求，不因 `mounted` 或整个工具 `ssr:false` 而消失 |
| metadata | 原本正确的Title、Description、H1、canonical等不无故改动；确需更改逐项说明 |
| 真实链接 | 用实际可抓取链接连接已发布目标；按钮负责动作，链接负责导航 |
| URL/发布 | 原路由保留；未发布对象不进入菜单或sitemap；筛选不制造大量索引页 |
| JSON-LD | 保留原有效声明，只反映真实可见内容；不虚构审核人、评分、课程或结果 |

[已核实] Google 文档建议考虑服务器渲染或预渲染，并强调可抓取链接；这不是排名或富结果保证。[S6、S10]

## 10. 导航、知识地图与内链

### 10.1 三层结构

```text
全站：保持现有栏目与主题，Chords仍是一个栏目
  └─ 和弦中心：按根音×类型查阅
      ├─ 当前页面里的基础说明
      ├─ 当前页面里的可用练习
      └─ 已发布的具体和弦详情
          ├─ 当前对象的参考与原有说明
          ├─ 有依据的左右手案例
          └─ 自查练习与相关下一步
```

不要照搬竞品的 `Major Chords / Minor Chords / More Chords / Premium` 整条导航，也不要增加不真实的全站搜索。

### 10.2 四页内的关系

| 起点与终点 | 关系及放置位置 |
|---|---|
| `/chords` ↔ 三个详情 | 目录/对象；结果入口与面包屑 |
| Am ↔ A major | 三度比较；放在对应解释旁 |
| C major ↔ Am | 只有明确的共同音/连接练习需要时呈现，不当成同根音大小比较 |
| 四页 → 已发布教程/音阶/进行 | 补充知识或应用；匹配具体上下文，不按一个字母粗暴关联 |

已有正确入口全部保留，最多调整分组和锚文本。新增关系建议具有 `targetId + relation + placement`，并验证目标的真实发布状态。

### 10.3 长期知识覆盖不是本轮发布清单

| 学习层次 | 覆盖提案 |
|---|---|
| 看懂符号 | 音名、音程、根音、音级、和弦符号 |
| 基础三和弦 | 大、小、减、增 |
| 怎样弹 | 原位、转位、排列、左右手、伴奏分工 |
| 更多类型 | sus、add、6、各种七和弦，再到扩展与变化 |
| 调内应用 | 调性、罗马数字、功能、终止、进行和连接 |
| 练习 | 构成、识别、听辨、反查；之后再评估设备输入 |

已有规划若包含 `/guide/piano-chords`、`/chords/by-key`、`/chords/finder`、`/chord-progressions`、`/keyboard-notes/finger-numbers`，保留规划，不据此直接创建或公开入口。

“根音 C 的和弦”与“C 大调调内和弦”必须分开。Slash 表达低音关系，不应与 major/minor 混成同一层互斥性质类别。[S8]

全站首页不加入整章和弦教程。本轮只改善四页和弦体系，不重新定义全站职责。

### 11.1 B1 设计预览，不再用新生成图猜主题

B1 使用真实代码、现有token和真实正文形成可浏览样板，沿用四页原路由中的两页做预览；不是新增正式可索引的设计稿路由。不发布到生产。

新模块只有真实文字或行为齐备才进入用户界面；未就绪部分写入规格和缺项，不放假的教学数据或可点击但无功能的CTA。工作区可用现有操作，其他新交互在报告中明确待实施。

输出桌面/手机全页与关键局部截图、交互状态表。没有实际浏览器验证，就只算代码草案，不能写“视觉验收通过”。

### 11.2 总体验收

**主题**：同一视口前后对比，背景、主色、Header、文字、控件与琴键高亮保持原主题；没有新的品牌装饰。

**内容**：全部原项目均有去向；正确内容丢失为0；任何纠错/删除都与批准清单一致。

**布局**：不把整页压进一个屏幕；无页面级意外溢出；长正文、步骤、表格能正常阅读。

**交互**：根音×类型、转位、音频停止、打印、键盘操作、错误/空状态均有复现证据。

**数据与SEO**：三页对象正确；核心HTML真实预渲染；canonical、链接、原静态资源与无JS能力无退化。

**范围**：共享组件有相应回归，至少检查受影响的其它页面；没有顺手改其余栏目的内容，没有部署。

**未验证项**：实机Safari、实体打印、人耳试听、真实读屏未执行时逐项列出，不用单元测试或模拟器冒充。

## 12. 交付文件与决策方式

R0 只需一份 `review.md`，附必要截图/日志在 `evidence/`。主题表、内容表、方案逐项判断和建议顺序放同一份报告，不制造十几个零散审核文件。

报告先给 `READY` / `READY_WITH_CHANGES` / `BLOCKED`，含义仅是“是否具备进入指定下一阶段的条件”。READY 不等于用户已经批准，不等于上线通过。

每个方案项用“采用 / 调整 / 暂缓 / 不采用”，写清证据、怎么改、为什么改。设计判断标为推断/建议，不声称有并不存在的用户数据。

实施后继续追加到 `implementation-log.md`，每批写范围、变更、测试、内容和主题检查、未完成项及停止位置。不得把“全部通过”当无证据的结尾。
