# PianoGrid 和弦系统 v2：怎么交给 Codex

日期：2026-09-11

**先审阅，再做真实主题的页面样板，确认后分批接数据和交互。不要把此前图片当成直接实现稿。**

## 1. 一共四个文件

| 文件 | 作用 |
|---|---|
| `00_START_HERE.md` | 你现在读的使用顺序 |
| `01_PROPOSAL_v2.md` | 修订后的完整提案：主题、内容保留、双维分类、页面顺序、交互、Schema、SEO与验收 |
| `02_REVIEW_PROMPT.md` | 第一轮给Codex：只读审阅，提出采用/调整/暂缓/不采用，不动业务代码 |
| `03_IMPLEMENT_PROMPT.md` | 你批准后才执行：每次只做B1、B2或B3中的一批 |

[已核实｜本包文件] 本包不包含之前的生成图，也不包含未经核实的新色值、现成指法数据或可直接覆盖项目的Schema实现。

这份v2替代旧提案中与它冲突的设计建议。旧文件可留在历史目录，不需要删除，但不要把两个版本同时当成执行规范。原始内容包、URL规划、项目代码和真实来源资料仍要保留。

## 2. 把文件放在哪里

将压缩包中的 `pianogrid-chords-v2` 文件夹放到项目的 `docs` 下：

```text
你的 PianoGrid 项目/
├─ 原有代码和文件（不移动、不覆盖）
└─ docs/
   └─ pianogrid-chords-v2/
      ├─ 00_START_HERE.md
      ├─ 01_PROPOSAL_v2.md
      ├─ 02_REVIEW_PROMPT.md
      └─ 03_IMPLEMENT_PROMPT.md
```

已有相同目录时检查内容，不覆盖用户已有报告。此前红色、蓝色、深色导航等生成图不要放进本轮批准设计目录，也不要要求Codex逐像素复刻它们。

主题依据不是你再找一个颜色给Codex，而是让它读取仓库里的真实主题与组件，并在当前浏览器页面上确认。代码/线上版本冲突才需要指出来确认。

## 3. 第一轮：先开一个Codex对话，只审阅

建议在能读取本地PianoGrid项目的Codex工作环境中打开这个仓库。不要只发网站地址或图片；本次审阅需要实际代码、主题和内容。

发送下面这段即可，不需要把所有长文件再次复制进聊天：

```text
请读取并执行 docs/pianogrid-chords-v2/02_REVIEW_PROMPT.md。

本轮只审阅 docs/pianogrid-chords-v2/01_PROPOSAL_v2.md
与当前实际仓库是否匹配，不修改业务源码、不改主题、不删除内容，
不开始实施、不提交、不部署。

重点核对：
1. 现站真实主题与组件；之前生成图的配色不作为依据。
2. 四页全部正确原内容和现有功能的保留与新位置。
3. 根音×类型、页面顺序、交互与Schema是否确实需要调整。

请给出采用/调整/暂缓/不采用的结论，
保存到 docs/pianogrid-chords-v2/review.md，然后停下。
```

[已核实｜官方资料] OpenAI的Codex实践建议对大改动先形成计划，并给出明确上下文和可分阶段验证的任务。这是本包流程的参考，不代表必须使用某个固定名称的界面按钮。[S1]

## 4. 怎么判断审阅结果可用

不要只看它是否写了“方案合理”。至少看清四件事：

| 你要看什么 | 合格结果 |
|---|---|
| 配色 | 指出真实token/类名、源文件和实际页面证据，不只是“沿用暖色风格” |
| 内容 | 原段落、FAQ、表格、图示、PDF与功能都有保留位置，没有以精简为由删正文 |
| 方案 | 能指出哪些已实现、哪些不需要做、哪些建议调整，不是照抄提案 |
| 下一步 | B1具体改哪些文件、怎样验证、什么不动，主题冲突是否已经解决 |

`READY`只是Codex对准备条件的判断，不代表你已经批准，不代表视觉或音乐内容自动正确。

有真正阻塞B1的问题时先解决该问题；来源未就绪的高级指法可以独立暂缓，不必让所有现有布局调整等待。

## 5. 第二轮：只批准B1，先看真实主题的样板

在同一个Codex对话里发送：

```text
我批准 docs/pianogrid-chords-v2/review.md 中审阅通过的方案。
本次只执行B1，按 docs/pianogrid-chords-v2/03_IMPLEMENT_PROMPT.md 操作。

先做 /chords 和 /chords/a-minor 两种完整页面样板。
沿用审阅确认的现有主题，保留所有正确内容与原有可用功能，
调整顺序、层级和留白，不按此前生成图取色。

未列入批准清单的删除、主题改动、依赖变更和新URL均不授权。
完成后给桌面/手机前后对照、交互说明和验证结果，然后停下。
不开始B2，不提交、不部署。
```

这一步的“设计稿”由真实项目代码和真实正文形成，不再是猜颜色的生成图片。不要只截首屏；也要检查长正文、原练习、FAQ和打印是否仍在。

## 6. 后面的批次

样板认可后，在同一对话按需批准：

```text
B1样板已确认。本次只执行B2，按03_IMPLEMENT_PROMPT.md执行。
复用已审阅的数据与组件，完成必要的Schema适配和三个详情的统一模板。
正确内容、主题、URL和预渲染不退化。完成后停下，不提交、不部署。
```

```text
B2结果已确认。本次只执行B3，按03_IMPLEMENT_PROMPT.md执行。
补齐审阅批准的增量分类体验、已核对内容和一个真实练习，完成四页验收。
没有证据的指法或功能不要虚构。完成后停下，不提交、不部署。
```

每批有问题就在该批修复，不要同时开三个修改共享组件的对话。对话容量不足或更换环境时再开新对话，明确读取同一份提案、`review.md`和`implementation-log.md`，不要依赖“延续上次”的模糊指令。

## 7. 今天做到什么程度就算完成

今天先完成R0：四个文件已放入项目；Codex实际读了代码；得到一份带主题证据、原内容去向和最小修改范围的 `review.md`。**今天不需要同时完成所有重构。**

最关键的顺序：

```text
真实仓库审阅
→ 你批准
→ 原主题的完整页面样板
→ 你确认版面
→ 必要的数据适配
→ 增量内容与交互
→ 验收后另行决定发布
```
