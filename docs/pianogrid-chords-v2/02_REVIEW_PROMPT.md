## 第三步：独立审阅方案，不机械执行

逐项判定以下事项：

- 两类母版及三个详情的内容差异是否合理？原页面是否已有合适结构？
- 现有根音×类型是否已经满足需求？是否只是交互展示需要改进？
- 两列卡片/单列长页面能否解决拥挤？是否有更小的布局调整？
- 默认不新增大侧栏是否适合当前代码？若建议统一预览，要说明原操作的去向和用户成本。
- 原内容怎样保留、重新排序？新增知识哪里确有缺口，哪里只会重复？
- 左右手案例有哪些真实来源，哪些不应发布？练习适合先做哪一个？
- Schema应复用、增加适配还是局部抽取？能否避免全局迁移和新依赖？
- 原始HTML是否已有正确内容？服务器预渲染、无JS、metadata和打印是否存在真实问题？
- 当前页内目录、四页内链与发布状态如何复用？哪些规划页面实际尚不可用？

每项只给一条主建议，必要时简述替代方案的取舍。不要给十套设计让用户重新选，不要扩展任务到全站重做。

对于来源、架构或体验结论使用：

- `[已核实]`：仓库、实际页面或可靠资料直接支持，注明位置。
- `[推断]`：解释依据，不写成实际用户统计。
- `[猜测]`：证据不足，不能作为自动实施的理由。

判断新的技术API时以项目实际版本为准。需要查文档可使用官方资料；没有网络就指出未验证，不声称完成核查。
