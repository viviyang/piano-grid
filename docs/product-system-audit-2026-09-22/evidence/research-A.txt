Executive Summary
[已核实] 这个案例真正值得研究的地方，不是“一个 EMD 域名靠一个 calculator 排起来了”，而是它把一个非常窄的
起点任务——“输入身体测量值，告诉我属于什么 body shape/body type”——扩展成了一条完整的需求链：测量
方法 → 计算 → 结果解释 → 相邻类型比较 → 单一体型知识页 → 穿搭 → 测量参考数据 → 男性版本 → WHR 等相邻
工具。当前首页本身已经不只是一个简单表单，而是支持女性/男性、英寸/厘米、实时 SVG 比例预览、结果比例
卡、雷达图、结果链接复制和图片下载；About 页面还明确写明该团队专注于“front-end product design、
measurement-content research、SEO publishing for practical tools”。
[推断] 因而，它更准确的模式不是：
Keyword → Article → 更多 Article
而是：
Keyword → Product Primitive → 输入前问题 → 结果 → 结果后的问题 → 独立工具/参考资产 →
内链闭环 → 更多可搜索任务
这正是你当初看到 body type calculator 却“不知道下一步应该做什么”时所缺的那一层：不是继续做关键词
扩展，而是先把关键词翻译成一个可执行的用户任务，再从任务前后推导网站。 这个结论也符合你在原始研究 brief
中提出的真正研究目标。fileciteturn0file0

[已核实] 当前 Google 搜索生态已经明显比“早期机会期”拥挤：现在可发现 DiscoverFashions、Calqulate、

Calculator Algorithm / Value
[已核实] 站点自己声称核心计算在浏览器端 JavaScript 完成，决策规则可检查，并强调这些 body-shape labels 是
fit/style shorthand，而不是完整科学模型。
公开内容暴露了部分决策阈值。例如 Pear comparison 页面将 hips − bust ≥ 3.6 in 作为核心 pear
separator；Apple 页面使用 WHR 与 bust/waist、hip/waist difference 共同处理 apple/rectangle 边界。
[已核实] 3.6 inch、9 inch 等类型阈值并非凭空出现：2004 年 Simmons、Istook、Devarajan 的 Female
Figure Identification Technique for Apparel (FFIT) 是服装人体形态分类体系，后续研究仍引用它；2020 年研
究甚至专门对 FFIT 公式进行修改以提高 plus-size body 的适用性。
这带来一个重要限定：
[已核实] FFIT 是 apparel/body-shape 分类方法，不是医学诊断系统，而且原公式并不对所有身体都完美。 2020
年的 plus-size 修改研究明确指出一些扫描会被错误分类或无法分类。
[推断] 所以目标网站真正的第一版技术门槛并不高。一个开发者需要：
找到合理的公开 apparel classification；
把输入、单位转换、阈值和边界条件编码；
把结果变成人能理解的解释；

最终回答十个成功标准
bodytypecalculator.org 怎么把一个词做成网站？
[推断] 它把 calculator 视为 journey 起点，然后围绕 input、classification、ambiguity、interpretation、action
建 URL，而不是围绕同义关键词堆文章。
哪几个页面真正承担增长？
精确答案 UNKNOWN；最可能的候选是主 calculator + female calculator + measurement/reference + type/
comparison clusters，但没有 Organic Pages report 不能给 traffic share。
Calculator 为什么有价值？
[已核实] 它把多个身体测量值转成可解释分类，并提供 ratio、visual result、分享和 next-step content。
Supporting pages 为什么存在？
[推断] 主要是解决输入错误、结果解释、边界分类和结果后的下一步，而不是单纯“增加 content”。
Backlinks 从哪里来？
完整组成 UNKNOWN；至少有公开 editorial citation，也有较强 portfolio/主动运营经验线索，但没有证据把 304
RD 全归因于任何单一来源。
增长多少来自执行、niche/timing/portfolio？
无法定量。执行层的 product/IA 可确认；portfolio 经验很可能有帮助；timing 和 backlinks 的因果权重 
UNKNOWN。
PianoGrid 能学什么？
围绕真实 task 建 tool/detail/reference/supporting pages，并把每次任务完成变成下一任务入口。
哪些绝对不能照抄？
EMD 迷信、近义词分页、追页面数、追 AS、无证据买 links、把模板规模化本身当增长战略。
时间回到当初，应做哪些验证？
Keyword → SERP intent gap → User Job → Input/Logic/Output → edge cases → next questions → keyword
validation → distribution → monetization → risk → MVP。
下次怎样更早发现类似机会？
看到关键词以后，不要先问“能写多少篇”，而先问：
“这个 query 能不能变成一个 state-changing product；结果之前和之后，是否各自存在真实需
求？”
