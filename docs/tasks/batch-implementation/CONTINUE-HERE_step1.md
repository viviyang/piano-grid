## 4. 每一批永远重复这一个流程

**开发 → 独立验收 → 有问题就修复、复验 → 你查看代表页 → 授权下一批。**

### A. 开发结束后：交给验收对话

确认开发已停止，在现有验收对话发：

```text
请读取 docs/tasks/batch-implementation/CONTINUE-HERE.md，执行“验收当前批次”。
开发已暂停；只输出验收报告和测试产物，不修改产品代码。
```

以后每一批都可原样使用这段。验收模型从唯一进度记录中定位待验收批次。

### B. 验收结果怎样处理

| 结果 | 你的下一步 |
| --- | --- |
| `PASS` | 看本批桌面、手机代表页；没有要改的，再发送下一批开发指令 |
| `PASS_WITH_NOTES` | 确认备注确实不阻塞本批任务；查看页面、接受备注后，可继续下一批 |
| `NEEDS_FIX` | 回开发对话，发送下面的修复指令；修完再发送上面的验收指令 |
| `BLOCKED` | 只处理报告指出的必要缺项或决策，不反复让模型重跑整个批次 |

开发自测通过，不等于独立验收通过。独立验收通过，也不等于用户已确认新页型视觉或允许部署。

### C. 有问题：回开发对话修复

```text

按当前批次的独立验收报告修复并回归；完成后停止等待复验，不进入下一批。
```

修完回验收对话，再发 A 中相同的验收指令，不需要另写新 Prompt。

## 7. 给 Codex 的稳定执行规则

### 7.1 每次先读取

1. 项目实际适用的 `AGENTS.md`。
2. `docs/tasks/batch-implementation/MASTER-RULES.md`。
3. `docs/tasks/batch-implementation/COMPONENT-TEMPLATE-RULES.md`。
4. `docs/tasks/site-implementation-plan.md`，以及相关实际源码和最新批次报告。
5. 当前动作对应的任务文件；实施/验收同时读该编号批次的完整范围。
6. 相关 `docs/design/design-system.md`、已有 `component-spec.md`、`template-map.md`，以及本批任务引用的产品、真实内容和资产。

依据用户本次的“动作＋批次”执行。读到本文件不等于获得所有批次授权。

找不到当前进度时，先找已有等价记录和报告，不重置到00；实际关键记录确实缺失才说明。不要用本文件中的用户完成反馈伪造本地验收记录。

### 7.2 动作：实施指定批次

- 用户明确点名某批，即授权该批任务和必要组件、模板、测试，不包括后续批次。
- 先简短确认已完成成果、前批是否存在真实阻塞、当前范围，然后执行；不要只输出一份新计划。
- 02 的首次接续只读核对01报告和进度，不无故重跑整个01。若01报告已通过且无阻塞，直接实施02；共享代码改动后的相关回归仍必须做。
- 对已实现部分复用、核对后保留。当前批次已完成待验收时，给出报告入口后停止，不重复开发。
- 有尚未解决的前批核心阻塞时，不冒称已通过；指出精确问题并保持范围约束。
- 在本批内部完成：检查现有实现 → 必要组件/模板 → 代表页验证 → 同批实例接入 → 自测和回归 → 更新记录。
- 组件文档不是交付终点。普通实现、模板提取与页面接入连续执行，不逐组件请示。
- 新任务沿用最终设计系统；不重新选风格，也不把不同任务都套成A minor页面。
- 仅在确有旧阶段限制妨碍本批授权时，最小更新 `AGENTS.md` 和检查脚本的阶段范围；不删除长期保护和失败断言。
- 复用实际依赖和测试工具，不重装已正常的依赖、不自动升级，不仅为整理目录而重构。
- 每个本批URL检查原内容/音乐数据、任务输出、资源、响应式与状态；同模板页面也不免核查。
- 完成后写 `checks/batches/<批次ID>/implementation.md`，维护既有组件/模板记录和唯一进度文件，然后停止待独立验收。

### 7.3 动作：验收当前批次

- 先按 `90-independent-review.md` 执行，同时执行组件补充规则中的复用验收要求。
- 从唯一进度记录及报告定位当前待验收或待复验批次；只有一个时直接进行。多个候选且无法判定时，只问批次编号，不猜。
- 确认开发已暂停；以当前代码和本轮证据审查，不直接继承上一批PASS或开发自测结论。
- 审查组件实际调用、模板与各页自身数据、最终设计一致性、真实任务功能和受影响旧页回归。
- 只写报告、截图和测试产物，不修改产品源码、源内容、依赖、规则或独立进度状态，不自行修复。
- 报告写 `checks/reviews/<批次ID>/review.md`。保留先前审查历史，不覆盖掉上一轮问题证据。
- 结论用 `PASS / PASS_WITH_NOTES / NEEDS_FIX / BLOCKED`，附实际证据与未测项。核心未交付不能降格为非阻塞备注。
- 完成后停止。下次主开发根据该报告更新原进度记录；不另建状态系统。

### 7.4 动作：修复当前批次

- 在主开发角色按 `91-fix-review.md` 执行。
- 读取唯一当前批次的 `review.md`；过时问题先对照当前代码复现。
- 只修已授权范围内的真实问题，补必要回归，不借修复换设计、升级依赖、改变音乐内容或开放新路由。
- 修复后跑相关测试、既有回归、check/build，记录真实结果。
- 写 `checks/batches/<批次ID>/fixes.md`，进度置为等待复验，不自己写成独立验收通过。
- 完成后停止，由验收角色用同一验收指令复验。

### 7.5 动作：恢复开发

按 `92-resume.md`，结合本文件接续当前已授权检查点。待验收就停止待验收；待修复就处理本批报告；只有用户明确指定下一批时才进入下一批。没有新授权时，不以“继续”解释为全站自动开发。

### 7.6 所有动作共同保留的边界

- 产品规划、URL、关键词、音乐数据、源内容和已确认视觉不改。
- 原始总包及 `preserved-chords/` 保持只读，新旧schema按已有适配读取。
- 不因旧内容包的“未准备”标记覆盖最新总包状态，也不因内容已准备就宣称代码、专业审阅或发布已完成。
- 原 `published`、`ready_for_publish` 不批量改true。保留已存在的本地预览白名单与生产链接限制，不能为隐藏生产未发布入口而误删本地联调导航。
- 只导出获准使用且本批实际需要的素材，不把内部文档和总JSON放进public。
- 本地验收通过不等于发布授权；不部署、不取消noindex、不自动commit/push。
- 测试只记录真正执行的范围，不把模拟、浏览器自动化写成真机、人工听音或实体打印。
- 无法解决的核心冲突精确定位到批次、URL、字段或环境问题；非核心缺项登记，不伪造，也不无故停止所有独立工作。

### 7.7 每次结束只汇报这五项

1. 本次处理哪个批次，当前状态是什么。
2. 已交付的页面/组件/模板或已修复问题。
3. 本地页面地址、真实截图与报告路径。
4. 实际测试结果、阻塞和未测项。
5. 用户下一步应当去哪个对话、发送什么短指令。

不要再生成另一份启动手册、另一套总计划或新的长Prompt。
